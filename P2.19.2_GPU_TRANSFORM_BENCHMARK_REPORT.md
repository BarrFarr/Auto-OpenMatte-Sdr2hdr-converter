## 2. GPU implementation

The isolated GPU function in `bench_p2192_gpu_transform.py` reproduces the current production stage order using CuPy arrays. Apart from the initial input upload and final output download, intermediate arrays remain on the GPU.

The GPU stages are:

1. BT.1886 EOTF: clip to `[0, 1]`, then power `2.4`.
2. Production BT.709 → BT.2020 matrix and nonnegative clamp.
3. Production BT.2020 luminance weights: `0.2627 / 0.6780 / 0.0593`.
4. Production 65,536-entry luminance curve LUT, including:
   - true-black behavior,
   - low-end black/bridge handling,
   - fitted-range index calculation,
   - curve maximum clamp.
5. Production safe ratio semantics: ratio remains `1.0` when luminance is not greater than `1e-6`.
6. RGB multiplied by luminance ratio and nonnegative clamp.
7. Optional production color-matrix branch and saturation branch are implemented; the benchmark transform uses the current identity defaults, so those branches are skipped exactly as in production.
8. Production 65,536-entry PQ OETF sqrt-LUT with linear interpolation.
9. Final production clamp to `[0, 1]`.

The CPU reference was not reimplemented. It calls the actual production function:

```text
auto_openmatte.processing.transform.apply_shot_transform
```

## 12. Speedup and bottleneck analysis

### Speedup

- CPU transform: `382.488 ms/frame`
- GPU transform only: `14.989 ms/frame`
- GPU total pipeline: `28.668 ms/frame`
- CPU / GPU transform-only: **25.52×**
- CPU / total GPU pipeline: **13.34×**

### Bottlenecks

1. **Host-device transfers:** separate upload and download medians total approximately `13.932 ms`, nearly half of the end-to-end GPU time.
2. **GPU transform:** the transform itself is approximately `14.989 ms` for this float64 parity path.
3. **Temporary memory:** the CuPy memory pool reserved a high-water proxy of approximately `758 MB`, with a `654 MB` transient reserved delta. This was measured only; no memory optimization was attempted.
4. **Host synchronization:** the total pipeline is deliberately synchronous so that transfer and computation are measured correctly. Pinned buffers, asynchronous streams, overlap, and batching were not tested.
5. **CPU utilization:** the host process remains active during the synchronous total pipeline. A production design would need to account for transfer orchestration and frame scheduling rather than assume the GPU eliminates all CPU work.

## 13. GO / NO-GO recommendation

### GPU feasibility: GO

The isolated GPU transform is numerically equivalent to the current CPU production transform within near-double-precision noise, passes all stated accuracy thresholds, passes the required edge cases and real-material ROI check, and provides:

- approximately **25.5×** transform-only speedup;
- approximately **13.3×** speedup including synchronous upload and download;
- finite, in-range output with no observed shadow plateau or white-dot regression.

### Direct production integration: NO-GO from this task

This benchmark does not justify directly integrating the GPU path into production yet. Integration remains a separate task because it requires an explicit decision about:

- transfer ownership and frame scheduling;
- pinned/asynchronous memory and stream overlap;
- float64 versus a separately validated float32 mode;
- temporary-memory reduction;
- multi-frame batching and error handling;
- production fallback behavior when CuPy/GPU is unavailable.

No integration was performed here, as required.
