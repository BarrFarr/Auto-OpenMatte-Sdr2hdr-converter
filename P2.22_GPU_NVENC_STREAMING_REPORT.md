# P2.22 GPU -> NVENC Streaming Prototype Report

**Date:** 2026-08-15  
**Scope:** Bounded experiment of `decode -> ROI -> transform -> NVENC`, maximum 10 frames.  
**Harness:** `P2.22_gpu_nvenc_probe.py`  
**Result:** A direct CuPy/GPU-transform -> NVENC zero-copy path is **not available through the current Python/repository interfaces**. The closest working FFmpeg CUDA path still starts with host memory and therefore does not remove the GPU -> CPU -> GPU boundary from the P2.20 backend.

## Executive answer

The requested path:

```text
decode -> ROI -> RTX 3080 GPU transform -> NVENC
```

cannot currently be implemented as a direct CuPy-device-frame -> NVENC pipeline without adding a native CUDA/FFmpeg interop layer.

What was verified:

- FFmpeg 7.1.1 can encode `hevc_nvenc` from host RGB input.
- FFmpeg 7.1.1 can run `hwupload_cuda -> scale_cuda -> hevc_nvenc`.
- The successful CUDA filter path is **host RGB -> FFmpeg software format conversion -> CUDA upload -> GPU p010 conversion -> NVENC**.
- The P2.20 Python backend returns a host NumPy `float64` array through `cupy.asnumpy()`. There is no CuPy pointer-to-`AVFrame`, `AVHWFramesContext`, or CUDA-frame ownership bridge in this repository.
- Therefore the actual measured GPU streaming variant remains:

```text
FFmpeg decode -> CPU RGB48 -> CPU float64 ROI -> GPU float64 transform
-> GPU->CPU download -> CPU RGB48 pack -> FFmpeg RGB->P010 -> NVENC
```

The bounded 10-frame measurements were:

| Variant | Meaning | Total | Effective FPS |
|---|---|---:|---:|
| A | CPU transform -> host RGB -> NVENC | **6109.1 ms** | **1.637 FPS** |
| B | GPU transform -> GPU->CPU -> host RGB -> NVENC | **3083.1 ms** | **3.244 FPS** |
| C | Direct CuPy->NVENC | **not available** | **not measurable** |
| C-prerequisite probe | Host RGB -> `hwupload_cuda` -> CUDA p010 -> NVENC | 341.5 ms for one frame, including process startup | not a direct-pipeline FPS |

The B GPU transform itself measured **15.260 ms median** by CUDA events, approximately 65.5 transform-only FPS in isolation. That is not the full streaming FPS. The full B pipeline is only 3.244 FPS because the measured decode, host conversion, ROI handling, GPU transfer, GPU transform, GPU download, RGB packing, and encoder stages are all on the path.

## 1. Current architecture and data flow

### Production/P2.20 backend

The relevant implementation is `src/auto_openmatte/processing/transform_backend.py`.

`GPUTransformBackend.transform_roi()` accepts a host NumPy array shaped `(height, width, 3)` and returns a host NumPy array with the same shape. Its steady-state path is:

1. Validate the host ROI.
2. Normalize the host array to contiguous `float64`.
3. Call `buffers.input_flat.set(...)`: host CPU -> persistent CuPy GPU input buffer.
4. Run the unchanged P2.20 float64 transform entirely on persistent GPU buffers.
5. Synchronize the null stream.
6. Call `cupy.asnumpy(buffers.output_flat)`: GPU -> host NumPy output.
7. Reshape the host output back to H x W x 3.

The transform math, LUTs, BT.1886, BT.709 -> BT.2020 matrix, low-end bridge, luminance curve, and PQ sqrt-LUT were not changed.

The P2.20 workspace was prepared once before the timed frames. For the `560 x 3840 x 3` ROI, the persistent report was:

- persistent ROI buffers: **849,408,000 bytes**;
- curve LUT: **524,288 bytes**;
- PQ LUT: **524,288 bytes**;
- matrix: **72 bytes**;
- persistent total: **850,456,648 bytes**;
- workspace allocations: **1**;
- pool reserved after preparation: **919,271,424 bytes**.

No shape changes occurred during the timed B variant.

### Existing renderer/NVENC boundary

`src/auto_openmatte/pipeline/render.py` still contains placeholder render entry points and does not implement a production frame loop. The closest existing experimental renderer is `test_p210_quick.py`, which already demonstrates a bounded host-memory pipe:

```text
FFmpeg raw RGB48 decode -> host NumPy -> CPU composition
-> uint16 RGB48 bytes -> FFmpeg stdin -> hevc_nvenc
```

The P2.22 harness intentionally did not modify this renderer or any production composition path.

### Exact A path

```text
10-frame FFV1 synthetic input
 -> FFmpeg decode to host rgb48le
 -> host uint16 -> float64 full-frame copy
 -> bottom ROI view, rows 1600..2159
 -> CPUTransformBackend float64 transform
 -> host float64 -> uint16 rgb48le pack
 -> host pipe to FFmpeg
 -> FFmpeg format=p010le/setparams
 -> hevc_nvenc
```

A has no explicit Python CPU -> GPU transform transfer. NVENC/FFmpeg may internally upload or map the host input, but that internal operation is not exposed as a separate Python-stage transfer.

### Exact B path

```text
10-frame FFV1 synthetic input
 -> FFmpeg decode to host rgb48le
 -> host uint16 -> float64 full-frame copy
 -> bottom ROI view, rows 1600..2159
 -> buffers.input_flat.set: CPU -> GPU
 -> P2.20 GPU float64 transform
 -> cupy.asnumpy: GPU -> CPU
 -> host float64 -> uint16 rgb48le pack
 -> host pipe to FFmpeg
 -> FFmpeg format=p010le/setparams
 -> hevc_nvenc
```

Thus B has the required GPU transform but still has the P2.20 GPU -> CPU output crossing. The subsequent FFmpeg encoder path receives host RGB and may perform another internal upload for NVENC. That second FFmpeg-side upload is implicit and was not counted as a CuPy operation.

### Exact C-prerequisite path

The successful FFmpeg-only CUDA probe used:

```text
host rgb48le
 -> format=gbrp16le
 -> hwupload_cuda
 -> scale_cuda=format=p010le
 -> hevc_nvenc with pix_fmt=cuda
 -> hevc_metadata bitstream metadata
```

This path proves that the installed FFmpeg can accept CUDA frames for NVENC. It does **not** prove that a CuPy allocation can be attached to that CUDA frame. The input still starts as host memory, and it never receives the P2.20 GPU transform output.

## 2. FFmpeg/NVENC capabilities verified in the environment

Environment:

- FFmpeg: **7.1.1 essentials build** at `C:\ffmpeg\bin\ffmpeg.exe`;
- ffprobe: `C:\ffmpeg\bin\ffprobe.exe`;
- GPU encoder: `hevc_nvenc` available;
- hardware acceleration: `cuda` available;
- relevant filters: `hwupload_cuda`, `hwdownload`, `scale_cuda`, `colorspace_cuda`;
- `hevc_nvenc` advertises `cuda` input support and 10-bit formats including `p010le`.

The installed encoder reports support for `p010le`, `yuv420p10le`-equivalent output negotiation, and `cuda` hardware frames. The P2.22 C-prerequisite command succeeded after explicitly converting host packed RGB48 to `gbrp16le` before `hwupload_cuda`:

```text
format=gbrp16le,hwupload_cuda,scale_cuda=format=p010le
```

The initial attempt without the software `gbrp16le` conversion failed with an FFmpeg filter-format negotiation error. This was corrected in the isolated probe; no production code was changed.

Repository-wide architecture inspection found no existing use of:

- `hw_frames_ctx`;
- `AVHWFramesContext`;
- CUDA `AVFrame` ownership;
- a CuPy pointer export/import into FFmpeg;
- a CUDA-aware Python encoder API;
- `hwupload_cuda` or `hwdownload` in project code.

Therefore the environment supports FFmpeg CUDA frames, but the current project does not have the interop layer required to hand the P2.20 CuPy output directly to NVENC.

### RGB -> YUV conversion measurement

The A/B encoder path contains FFmpeg’s RGB48 -> P010 conversion inside the FFmpeg graph, so it cannot be isolated from the same pipe with a single process wall timer. The harness therefore ran an additional bounded 10-frame conversion-only probe:

```text
raw rgb48le -> format=p010le -> setparams -> null muxer
```

Result:

- software conversion-only wall time: **99.015 ms for 10 frames**;
- representative conversion: **9.902 ms/frame**;
- this value is not added to A/B totals because the A/B totals already contain the conversion inside FFmpeg/NVENC.

The C-prerequisite path instead performs the color conversion on CUDA through `scale_cuda`, but it starts from a host RGB frame and is only a one-frame capability probe.

## 5. Synchronization

### A

- No CuPy/CUDA synchronization.
- Python waits for decoder pipe reads.
- Python writes and flushes each packed frame to FFmpeg stdin.
- Closing stdin and waiting for FFmpeg accounts for pending encode work.

### B

For each timed frame, the isolated staged implementation used:

1. null-stream synchronization before the upload stage;
2. upload start/end CUDA events and end-event synchronization;
3. transform start/end CUDA events and end-event synchronization;
4. download start/end CUDA events and end-event synchronization;
5. final null-stream synchronization after download.

The per-operation trace did not synchronize after each transform kernel. CUDA event elapsed times therefore measure stream work without changing the kernel launch graph. The public backend correctness pass also exercised its normal `transform_roi()` behavior: null-stream synchronization before `cupy.asnumpy`, followed by the implicit materialization wait in `cupy.asnumpy`.

### FFmpeg/NVENC

The host pipe write may block if FFmpeg/NVENC backpressure occurs. The pipe-write statistic is therefore host-side backpressure time, not a pure NVENC kernel time. The encoder finalization wait is measured separately, but FFmpeg does not expose a per-frame NVENC CUDA event through this Python harness.

## 6. Copy and transfer audit

For each decoded full frame:

- host decoded RGB48 bytes: **49,766,400 bytes** (`3840 x 2160 x 3 x 2`);
- host uint16 -> float64 full-frame conversion: one full-frame host copy, approximately **99,532,800 bytes** of float64 storage;
- ROI extraction: **0-byte view** for the contiguous host frame;
- ROI float64 payload: **51,609,600 bytes**;
- RGB48 output to FFmpeg: **12,902,400 bytes/frame** (`3840 x 560 x 3 x 2`).

B additionally performs:

- CPU -> GPU input upload: **51,609,600 bytes/frame**;
- GPU -> CPU output download: **51,609,600 bytes/frame**;
- host float64 output -> RGB48 pack: a new uint16 output buffer;
- host RGB48 pipe -> FFmpeg, after which FFmpeg/NVENC may perform an implicit GPU upload.

The P2.22 probe found no direct CuPy-to-AVFrame transfer. Therefore B does contain a GPU -> CPU -> FFmpeg-host-input boundary, and a later FFmpeg/NVENC upload is possible. No production GPU frame object is shared with FFmpeg.

## 10. Performance decision

### A. Is direct GPU -> NVENC possible now?

**Not from the current P2.20 Python/CuPy backend.** FFmpeg supports CUDA frames, but the repository has no mechanism to export the P2.20 CuPy allocation as an FFmpeg `AVFrame` backed by an `AVHWFramesContext`. The verified C-prerequisite path is not direct because it begins with host RGB and uses `hwupload_cuda`.

### B. Cost of GPU -> CPU transfer

For the B ROI:

- CUDA-event GPU -> CPU download median: **7.130 ms**;
- bytes transferred: **51,609,600 bytes/frame**;
- P95: **7.595 ms**;
- separately, host RGB48 packing after the download costs **33.269 ms median**.

The download is material, but the subsequent host pack is larger than the measured download and the decode/host conversion stages are larger still.

### C. Is transfer the bottleneck?

The GPU -> CPU transfer alone is **not the largest full-pipeline bottleneck** in this probe. B’s dominant measured components are:

- decode RGB48 read: approximately **140.8 ms median**;
- host RGB16 -> float64 conversion: approximately **63.9 ms**;
- RGB48 output pack: approximately **33.3 ms**;
- GPU upload + transform + download events: approximately **29.8 ms** by adding their medians;
- encoder finalization amortization: approximately **7.6 ms/frame**.

The transfer remains a reason to pursue a native device-frame path, but removing it alone would not make this current host-decode/host-conversion pipeline reach 24 FPS.

### D. Does the measured streaming path exceed 24 FPS?

**No.** The complete measured B path is **3.244 FPS**. A is **1.637 FPS**. The isolated B transform event corresponds to approximately 65.5 median FPS, but that is not a streaming result and includes neither decode nor encode.

### E. Current theoretical/observed FPS

The only defensible values from this experiment are:

- A measured full pipeline: **1.637 FPS**;
- B measured full pipeline: **3.244 FPS**;
- B median GPU transform event alone: **65.53 FPS**;
- B median upload + transform + download event sum: approximately **33.53 FPS**, before host decode/conversion/packing/encode;
- C direct CuPy pipeline: **no FPS**, because it was not available;
- C host-upload capability probe: one frame in **341.5 ms**, including FFmpeg process startup, not a streaming FPS measurement.

No direct-path FPS estimate is claimed because there was no direct-path measurement.

### F. Next bottleneck

For the measured B pipeline, the next bottlenecks are host-side:

1. FFmpeg decode to full-frame host RGB48;
2. host uint16 -> float64 full-frame conversion;
3. host RGB48 packing after the GPU download;
4. then GPU scheduling/transform variance, including one approximately 81 ms transform sample in this 10-frame run.

NVENC pipe writes were approximately 1.15 ms median; that metric is host pipe/backpressure time and is not a complete NVENC hardware timing, but it does not indicate that the encoder pipe itself dominated this run.

## 11. Limitations

- The source was a generated 10-frame `testsrc2` clip because no source movie is committed to the repository and the production renderer is intentionally still a placeholder.
- The probe measures a bottom 560-row ROI, not a complete Mode A HDR/Open Matte composite. The HDR-overlap check was run separately on a bounded synthetic composition.
- The real jacket ROI was not evaluated against the external Blade Runner media; its reported values are synthetic diagnostics only.
- `cupy.asnumpy()` and the public P2.20 API necessarily return host arrays. No direct CUDA pointer interop was available.
- RGB -> YUV conversion is internal to the A/B FFmpeg graph; the separate 9.902 ms/frame conversion probe is representative and bounded, not a per-kernel encoder measurement.
- FFmpeg/NVENC CUDA kernel timings were not available through this Python pipe harness. A native FFmpeg trace or Nsight capture would be required for that level of attribution.
- C demonstrates a host-upload CUDA path, not a direct CuPy-to-NVENC path.

## 12. Recommended next step

Do not integrate C into production and do not change the P2.20 backend based on this prototype.

If the direct path is reopened, the next diagnostic/engineering step is a separate native interop prototype that:

1. owns an FFmpeg `AVHWFramesContext` on CUDA;
2. exposes a CUDA-backed `AVFrame` to the encoder;
3. defines ownership and synchronization between the transform stream and NVENC;
4. performs RGB -> p010/YUV420 conversion on device;
5. either wraps a compatible CUDA allocation or moves the transform into an FFmpeg/CUDA filter boundary.

That work must first establish a valid device-frame contract. It should not be implemented by adding an implicit `cupy.asnumpy()`/`hwupload_cuda` pair and calling it zero-copy.
