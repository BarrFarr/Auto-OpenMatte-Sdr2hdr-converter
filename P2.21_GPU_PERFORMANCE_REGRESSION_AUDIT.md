# P2.21 GPU Performance Regression Audit

**Date:** 2026-08-15  
**Scope:** Read-only audit of the reported P2.19.2 `~15 ms` versus P2.20 `~60 ms` GPU transform difference.  
**Decision:** During this audit, no production implementation, mathematical, workspace, default, rendering, dtype, commit, or push changes were made.

## Executive conclusion

The reported `~60 ms` P2.20 GPU transform time is **not reproducible as a stable computational regression** under a controlled comparison.

Using the same fixed `float64` input (`np.random.default_rng(2192).random((560, 3840, 3), dtype=np.float64)`), separate clean Python processes, five warmups, and twenty timed iterations:

| Implementation | GPU transform timing | Total timing |
|---|---:|---:|
| P2.19.2 existing temporary-array benchmark | **14.496 ms median**; 14.772 ms mean; 13.749–16.207 ms | 28.500 ms median |
| P2.20 current persistent-buffer backend | **14.629 ms median**; 14.404 ms mean; 13.555–15.037 ms | 26.192 ms staged total; 26.972 ms public `transform_roi` wall time |

The unchanged material-like P2.20 benchmark was subsequently rerun and remained highly variable: transform CUDA-event median **25.800 ms**, mean **69.454 ms**, range **13.818–199.825 ms**. This is direct evidence that the earlier `60.095 ms` value was a transient/high-variance benchmark outcome, not a repeatable P2.20 kernel-time penalty.

The audit therefore establishes:

1. There is no deterministic P2.20 transform regression from approximately 15 ms to approximately 60 ms in the controlled reproduction.
2. The observed difference is explained by run-to-run GPU/host/system timing variability together with non-equivalent benchmark boundaries and workload setup.
3. The exact low-level CUDA scheduler, launch, or kernel mechanism behind individual slow samples is **not proven** by this audit. A kernel timeline such as Nsight Systems/Compute would be required.
4. The correct action is to stop. No optimization should be implemented based on the original `~60 ms` sample.

## 1. Compared implementations and benchmark boundaries

### P2.19.2

Source/benchmark: `bench_p2192_gpu_transform.py`

- Uses temporary 3-D CuPy expression arrays during the transform.
- Uses one transform-wide CUDA event interval for the GPU transform measurement.
- Performs explicit default-stream synchronization around input upload, transform timing, and output materialization.
- The benchmark's input generation, setup, scaling sequence, allocator behavior, and CPU timing wrapper differ from P2.20.
- The transform-only CUDA event excludes the host-to-device and device-to-host portions represented by the separate wall-clock stages.

### P2.20

Source/backend: `bench_p220_gpu_backend.py`, `src/auto_openmatte/processing/transform_backend.py`

- Uses persistent flat `float64` buffers sized for the active ROI.
- Uses explicit `out=`, `copyto`, and `take` operations against the workspace rather than relying on the same temporary 3-D expression allocation pattern as P2.19.2.
- Separates upload, transform, and download stages and synchronizes each stage in the staged audit harness.
- The public `GPUTransformBackend.transform_roi` synchronizes the null stream before `cupy.asnumpy`; `cupy.asnumpy` also materializes/waits for the result.
- Uses a different input generator and material-like benchmark setup from the P2.19.2 benchmark.
- Uses a different scaling order and CuPy memory-pool history. Resizing the persistent workspace increases the allocation count and changes allocator state.
- The production backend remains optional; CPU remains the default.

These differences can change the measured wall time and the probability of observing a delayed GPU event. They do not explain a stable 45 ms increase in the controlled transform event: P2.20 measured 14.629 ms in that comparison.

## 2. Stage timing for P2.20

The stage trace used non-blocking CUDA event pairs around selected module-level CuPy calls. It did **not** synchronize after every kernel; one final event wait was used to collect the trace. The trace covered 41 expected CuPy calls per transform. The following values are medians from three trace runs and are CUDA-event times, not host wall-clock estimates.

| Stage | CUDA-event time (ms) | Instrumented operations |
|---|---:|---|
| B. BT.1886 linearization | **2.984** | clip and power |
| C. BT.709 -> BT.2020 matrix | **6.109** | matrix multiply and clamp |
| D. BT.2020 luminance | **0.466** | channel multiply/add operations |
| E. Luminance curve LUT | **0.609** | comparisons, index arithmetic, LUT/take/copy operations |
| F. Ratio | **0.236** | comparisons, division, and copy operations |
| G. RGB x ratio | **0.180** | multiply |
| H. RGB clamp | **0.156** | clamp |
| I. PQ sqrt-LUT | **2.413** | sqrt-LUT index/interpolation operations |
| **Sum of listed stages** | **13.152** | Does not include untraced device assignments and all launch/ordering overhead |
| **Outer transform event** | **14.464** | Whole `_transform_device` event interval |

The matrix operation is the largest traced stage, followed by BT.1886 linearization and PQ LUT processing. The sum of the selected calls is lower than the outer interval by approximately 1.31 ms; this is expected because the trace intentionally excludes some array-method operations and does not equate the sum of individual kernel intervals with the complete stream interval.

Untraced device operations reported by the instrumentation were:

- `buffers.mapped_luminance.fill(0.0)`;
- `buffers.lower[...] = buffers.position * (lut_size - 1)`;
- `buffers.pq_lower[...] = buffers.pq_position`.

No per-kernel synchronization was added for this measurement, because doing so would change the workload being audited.

## 3. Synchronization audit

### P2.19.2 transform benchmark

The static and runtime audit found:

- default-stream synchronization before timed iterations;
- one end-event synchronization for the transform-wide CUDA event;
- synchronization around upload and output materialization paths;
- `cupy.asnumpy` for GPU-to-CPU materialization, which waits for the required work;
- setup-time synchronization for device LUT/matrix initialization.

The transform-only result is therefore a CUDA-event measurement bounded around the transform, while the complete wall-clock result also includes transfer and wait boundaries.

### P2.20 staged audit harness

For each timed staged ROI, the harness performed:

1. one null-stream synchronization before starting the staged measurement;
2. one end-event synchronization after the upload event;
3. one end-event synchronization after the transform event;
4. one end-event synchronization after the download event;
5. one null-stream synchronization after the staged measurement.

These waits make the staged timings complete and observable; they are not hidden per-kernel waits.

### P2.20 public backend

`GPUTransformBackend.transform_roi` performs one null-stream synchronization after `_transform_device` and before `cupy.asnumpy`. `cupy.asnumpy` is a GPU-to-CPU operation and implicitly waits/materializes the output. This is a real host wait in the public wall-clock path, but it does not account for a deterministic 60 ms transform event: the controlled P2.20 transform event was 14.629 ms median.

### Initialization-only synchronization

- `prepare_shot` enters the selected device context, uploads LUT/matrix state, and performs one null-stream synchronization after setup.
- First-shape allocation and upload are asynchronous until the explicit audit synchronization.
- Initialization and first allocation are excluded from the steady-state 20-iteration transform timing.

## 4. Copy and transfer audit

For the primary `560 x 3840 x 3` ROI:

| Transfer or operation | Size/type | Frequency/scope |
|---|---:|---|
| Host -> GPU input | **51,609,600 bytes**; `float64` | Once per timed ROI |
| GPU -> host output | **51,609,600 bytes**; `float64` | Once per timed ROI |
| Host normalization | **0 bytes copied** | C-contiguous `float64` input; `np.asarray(order='C')` is a same-layout view/reference |
| Host reshape | **0 bytes copied** | `reshape(-1, 3)` is a view for the contiguous input |
| Curve LUT setup | **524,288 bytes**; 65,536 `float64` entries | Once during backend setup |
| PQ LUT setup | **524,288 bytes**; 65,536 `float64` entries | Once during backend setup |
| Matrix setup | **72 bytes** | Once during backend setup |
| Curve scalar parameters | **24 bytes** | Once during backend setup |

Steady-state GPU-to-GPU operations include index assignments, three curve masked `copyto` writes, two PQ `take` writes, two weighted PQ multiplies, and one output add. The audit found **zero additional full-ROI host copies** in steady state and no host normalization or reshape copy for the controlled input.

The explicit `out=`/workspace operations are additional device work compared with a simple expression graph, but their measured controlled transform time is approximately 14.6 ms. The audit does not claim that every internal CuPy implementation detail has zero transient device allocation; it establishes that the persistent workspace allocation count remained stable during the primary timed loop and that no additional full-ROI host copy was introduced.

Measured stage wall times in the controlled P2.20 run were:

- upload CUDA event median: **4.239 ms**;
- transform CUDA event median: **14.629 ms**;
- download CUDA event median: **7.416 ms**;
- staged total wall median: **26.192 ms**;
- public backend `transform_roi` wall median: **26.972 ms**.

## 8. GPU telemetry

Telemetry was available through `nvidia-smi` for an NVIDIA GeForce RTX 3080 with 10,240 MiB total memory, CUDA compute capability 8.6, CuPy 14.1.1, and CUDA runtime 13.02.

During the controlled P2.20 timed loop, sampled telemetry was approximately:

- GPU utilization: **27–40%**;
- memory utilization: **6–12%**;
- power: **97–110 W**;
- SM clock: **1755–1800 MHz**;
- memory clock: **9251 MHz**;
- device memory used: approximately **2643–2684 MiB**.

P2.19.2 before/after snapshots were 12%/99% GPU utilization, 1%/42% memory utilization, 64.73/110.01 W, and 1755/1800 MHz. These are coarse snapshots, not a kernel timeline.

The P2.20 timed-loop utilization was not near sustained saturation. That observation is compatible with short kernels, launch/stream gaps, host waits, or transient scheduling effects, but it cannot distinguish among them. No claim of compute-bound or memory-bound behavior is made from `nvidia-smi` alone.

## 10. Root cause assessment

### Confirmed

- The original `~60 ms` P2.20 transform value is not reproducible as a stable result under a clean, controlled 5+20 run.
- P2.19.2 reproduces at approximately 14.5 ms transform time.
- P2.20 reproduces at approximately 14.6 ms transform time with the same fixed input, ROI, dtype, and separate-process setup.
- The unchanged P2.20 material-like harness produces large outliers, including approximately 199.8 ms transform-event samples, while also producing approximately 13.8–16.1 ms samples.
- Therefore the observed `15 ms -> 60 ms` difference is dominated by timing/run variability and non-equivalent benchmark boundaries, not by a demonstrated deterministic P2.20 mathematical or kernel regression.

### Observed contributing conditions

- Different input generation and benchmark setup.
- Different CPU wall-clock boundaries and staged synchronization boundaries.
- Different persistent-workspace and temporary-array execution patterns.
- Different scaling order and CuPy allocator/pool history.
- GPU/host timing variability visible in repeated CUDA-event samples and low/intermittent `nvidia-smi` utilization.

### Not proven

This audit cannot identify the exact CUDA scheduler, kernel-launch, OS scheduling, power-management, or driver-level mechanism responsible for any individual 60–200 ms event. No Nsight Systems/Compute kernel timeline, per-kernel launch trace, or continuous power-state history was available. CUDA events and source inspection alone are insufficient to prove that mechanism.

## 11. Recommendation

Do not optimize, refactor, change synchronization, reduce workspace, change stream policy, change dtype, or alter production defaults based on the original `~60 ms` sample. The controlled evidence does not justify a production performance change.

If the issue is reopened, the next diagnostic—not an optimization—should be a paired Nsight Systems/Compute capture using identical input, process isolation, warmup, scaling order, stream policy, and timing boundaries. Capture continuous GPU clocks, power state, host scheduling, kernel launches, and stream gaps. Until that trace exists, report the result as high-variance/transient rather than as a confirmed P2.20 regression.
