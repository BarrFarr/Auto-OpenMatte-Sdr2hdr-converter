# P2.20 GPU Backend Integration Report

## Executive result

**GO for the isolated experimental float64 backend and composition API.** The GPU implementation matches the unchanged CPU transform within the acceptance limits, preserves the existing LUT/curve/geometry/compositing semantics, reuses one per-shot workspace for repeated same-shape ROIs, and falls back permanently to CPU after GPU availability or runtime failure.

**NO-GO for default production video rendering.** The active render functions are still placeholders, and the GPU path is intentionally not enabled by default. The CLI flag is an explicit forward-compatible opt-in; a future frame loop must create and retain a backend/workspace per shot before the GPU path can be used for a video render.

Scope was intentionally stopped after backend implementation, focused tests, benchmark, memory analysis, and this report. No full-film render, 10-second render, float32 production change, commit, or push was performed.

## Scope and protected behavior

The backend is an implementation of the existing `apply_shot_transform()` algorithm, not a new color pipeline. The following remain unchanged:

- fitting domain and P1–P99.9 analysis semantics;
- PCHIP reference and the production 65,536-entry luminance curve LUT;
- low-end bridge, true-black handling, safe-ratio threshold, and top-end clamp;
- BT.1886/BT.709 linearization;
- BT.709 to BT.2020 matrix and nonnegative clamp;
- BT.2020 luminance weights and ratio scaling;
- optional color-matrix and saturation branches;
- cached 65,536-entry sqrt-spaced PQ OETF LUT;
- PQ/HDR transfer behavior and peak-nits handling;
- ROI geometry, extension selection, feather behavior, compositing, and HDR overlap placement.

`src/auto_openmatte/processing/transform.py` and `src/auto_openmatte/processing/luminance.py` have no diff from this work. The CPU implementation remains the reference implementation.

## Architecture

The public backend contract is:

```text
prepare_shot(transform, sdr_transfer, hdr_transfer, peak_nits)
    -> persistent TransformWorkspace

transform_roi(om_frame, transform, workspace, ...)
    -> one host NumPy output ROI
```

### CPUTransformBackend

`CPUTransformBackend` delegates to the unchanged `apply_shot_transform()` and passes a per-shot `build_curve_lut()` result through `prebuilt_lut`. It is the default implementation and remains available as the numerical reference.

### GPUTransformBackend

`GPUTransformBackend`:

1. imports CuPy lazily;
2. validates the CUDA device only when the backend is first used;
3. currently supports the production `bt709 -> smpte2084` pair;
4. builds the curve LUT on CPU and copies its float64 arrays to the GPU once per shot;
5. copies the process-cached PQ sqrt LUT to the GPU once per GPU backend;
6. keeps intermediate arrays on the GPU;
7. transfers one input ROI to a reusable float64 input buffer;
8. executes linearization, gamut conversion, luminance curve, optional color/saturation processing, and PQ LUT encoding on the GPU;
9. transfers one output ROI back to the CPU.

The benchmark instrumentation calls the backend's staged internal methods only to expose upload/compute/download timings. Normal callers use the public `transform_roi()` method.

### FallbackTransformBackend

`create_transform_backend(experimental_gpu=False)` returns `CPUTransformBackend`. With `experimental_gpu=True`, it returns a GPU-primary `FallbackTransformBackend` with a CPU fallback.

Fallback is sticky for the lifetime of the wrapper. It switches to CPU when any of these occur:

- CuPy import fails;
- no requested CUDA device exists;
- GPU initialization or shot/LUT setup fails;
- an GPU transform raises `BackendRuntimeError`.

The fallback recomputes through the CPU reference and does not silently continue attempting a failed GPU path on every frame.

## LUT lifecycle and persistent workspace

For each transform signature/shot:

- the CPU luminance curve LUT is built once;
- the 65,536-entry curve LUT is copied to GPU memory once;
- the 65,536-entry PQ sqrt LUT is copied to GPU memory once per GPU backend;
- all LUT arrays are float64;
- LUTs are shared across subsequent ROIs for that shot and are not copied per frame, channel, or transform.

The GPU workspace owns a reusable `_GPUBufferSet` for each currently requested ROI shape. For the benchmark's fixed 560x3840 extension ROI, all 10 timed ROIs reused the same buffer object and reported exactly one workspace allocation. Shape changes intentionally allocate a buffer set for the new shape; this is discussed under limitations.

## Composition and production safety

`composite_extend()` and `composite_convert_hdr()` accept optional trailing `backend` and `backend_workspace` arguments. With no backend, existing direct CPU calls remain the default. With a backend, only the regions that were previously transformed by the composition code are routed through it:

- top extension;
- bottom extension;
- left/right extension strips when present;
- overlap pixels only when the existing feather mask requires transformed OM pixels.

Pure HDR overlap placement remains direct HDR placement. The overlap invariance test confirms that the GPU backend does not transform or replace those HDR pixels.

`RenderConfig.experimental_gpu` defaults to `False`. The `extend` and `convert-hdr` CLI commands expose `--experimental-gpu`, but `render.py` currently returns from placeholder render functions and has no active frame loop. Therefore this flag does not claim to have rendered a video; it provides the explicit configuration boundary for future render-loop integration.

## Benchmark setup

Results are from `P2.20_gpu_backend_benchmark_results.json`, generated by `bench_p220_gpu_backend.py`.

- GPU: NVIDIA GeForce RTX 3080, compute capability 8.6, 10,736,893,952 bytes device memory;
- CuPy 14.1.1, CUDA runtime 13.2;
- dtype: float64 throughout the GPU path;
- primary ROI: 560x3840x3;
- 2 warmups plus 10 sequential timed ROIs;
- one ROI/frame at a time; no film or sequence precomputation;
- CPU reference: `CPUTransformBackend` over the unchanged production transform;
- GPU transform timing: CUDA events;
- upload/download timing: CUDA events around the staged backend operations;
- scaling: 3 runs each for 280x3840, 560x3840, and 1080x1920.

### Primary 560x3840 timing

All values are milliseconds unless noted. FPS is calculated from the median.

| Stage | Median | Mean | Min | Max | FPS from median |
|---|---:|---:|---:|---:|---:|
| CPU backend transform | 358.605 | 360.180 | 349.700 | 374.157 | 2.789 |
| CPU → GPU upload | 7.857 | 7.770 | 6.788 | 8.773 | 127.276 |
| GPU transform, CUDA events | 60.095 | 61.851 | 14.482 | 125.556 | 16.640 |
| GPU → CPU download | 8.302 | 7.911 | 6.134 | 10.919 | 120.453 |
| Total upload + transform + download | 76.207 | 77.747 | 28.021 | 142.849 | 13.122 |

The latest run contains substantial GPU scheduling variability: five transform samples are near the low-latency range while several are approximately 98–126 ms. The median results are reported as observed, not smoothed or discarded. Relative to the latest run's medians, CPU/GPU transform speedup is **5.97x**, and CPU/GPU total-path speedup is **4.71x**. The earlier P2.19.2 isolated implementation measured a more stable 25.52x transform-only and 13.34x transfer-inclusive speedup; the variability in this P2.20 backend is a reason not to claim production readiness from performance alone.

### Accuracy

Across the 10 primary timed ROI comparisons:

- maximum RGB difference: **8.33e-17 normalized**;
- maximum BT.2020 luminance difference after PQ decode: **4.20e-14 nits**;
- acceptance limits: `1e-5` RGB and `0.01` nits;
- result: **PASS**.

The result is many orders of magnitude inside the acceptance limits and is consistent with a float64 implementation of the same LUT and transform stages.

### Scaling observations

Each scaling row uses three timed runs after a size warmup. The GPU total includes upload, transform, and download.

| ROI | CPU median | GPU total median | GPU transform median | GPU buffer allocations |
|---|---:|---:|---:|---:|
| 280x3840 | 177.789 ms | 14.745 ms | 7.121 ms | 2 |
| 560x3840 | 350.983 ms | 45.087 ms | 28.825 ms | 3 |
| 1080x1920 | 338.881 ms | 108.587 ms | 92.387 ms | 4 |

These short scaling runs are diagnostic rather than a sustained throughput certification. Their timing variability reinforces that a future production render needs longer stability testing and explicit GPU scheduling/stream policy before relying on the best-case values.

## Memory analysis

For the fixed primary 560x3840 ROI after warmup:

- persistent ROI buffers: **849,408,000 bytes**;
- curve LUT: **524,288 bytes** (`65,536 * float64`);
- PQ LUT: **524,288 bytes** (`65,536 * float64`);
- BT.709→BT.2020 matrix: **72 bytes**;
- persistent workspace total: **850,456,648 bytes** (approximately 811 MiB);
- CuPy pool used: **850,458,624 bytes**;
- CuPy pool reserved: **919,271,424 bytes**;
- free device memory: **8,570,011,648 bytes** of **10,736,893,952 bytes**.

Warmup and main-ROI-final counters are identical, and all 10 fixed-shape timed ROIs retain `workspace_allocations=1`. This demonstrates no per-frame persistent-buffer growth for a fixed geometry/ROI shape.

The scaling diagnostic changes shapes in one workspace. The final shape-specific buffer set is retained, while CuPy also keeps previously freed blocks in its allocator pool:

- post-scaling pool reserved: **2,732,519,424 bytes**;
- post-scaling live persistent bytes: **820,120,648 bytes**;
- shape allocations: **4**;
- observed pool high-water growth is allocator caching after shape changes, not a new allocation on each frame of the fixed primary ROI.

This is a limitation to address before a production renderer changes ROI shapes frequently. `GPUTransformBackend.clear()` drops backend references; a future render owner can also trim CuPy's memory pool at shot/shape boundaries where appropriate. No forced pool trimming was added in this task because the benchmark's purpose was to measure the current correct implementation rather than hide allocator behavior.

## Limitations and follow-up gates

1. **Active render loop is not implemented.** The render functions are placeholders. Future integration must retain one backend/workspace per shot and pass it through the frame loop.
2. **Transfer-pair coverage is intentionally narrow.** The GPU implementation currently supports `bt709 -> smpte2084`; unsupported pairs use CPU fallback.
3. **Performance variability remains.** The latest CUDA-event run contains large outliers. Repeatability and sustained multi-shot behavior need investigation before production enablement.
4. **Shape changes increase allocator high-water memory.** Fixed geometry is the intended streaming mode; shape lifecycle and pool trimming need a deliberate policy.
5. **Float64 is intentional for P2.20.** No float32 production path was added. Float32 belongs to the separate P2.21 experiment.
6. **No multi-GPU or asynchronous pipeline policy was introduced.** The implementation uses the selected device and default stream, leaving future scheduling decisions explicit.

## Final GO/NO-GO decision

- **GO:** isolated experimental float64 backend, CPU/GPU shared interface, persistent per-shot LUT/workspace behavior, CPU fallback, optional composition routing, parity tests, and benchmark artifact.
- **NO-GO:** making GPU the default, claiming completed video-render integration, enabling float32 production, or using the current benchmark alone as a production performance guarantee.
