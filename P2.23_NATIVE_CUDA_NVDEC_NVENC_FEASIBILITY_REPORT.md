# P2.23 Native CUDA NVDEC → NVENC Feasibility Report

**Date:** 2026-08-15  
**Scope:** Bounded feasibility probe, exactly 10 frames, no CuPy, no custom transform, no production changes.  
**Harness:** `P2.23_native_cuda_probe.py`  
**Results:** `P2.23_native_cuda_probe_results.json`  
**Decision:** **PASS** — this computer and this FFmpeg build can keep the decoded video frame in CUDA memory from NVDEC through CUDA processing to NVENC.

## Executive answer

The requested native path is available:

```text
HEVC BR2049
  -> hevc_cuvid / NVDEC
  -> AVFrame with format=cuda
  -> CUDA filter operation
  -> CUDA frame with p010le software format
  -> hevc_nvenc / NVENC
  -> HEVC Main 10 HDR10
```

The successful runs used:

```text
-hwaccel cuda
-hwaccel_output_format cuda
-c:v hevc_cuvid
...
-c:v hevc_nvenc
-pix_fmt cuda
```

The verbose FFmpeg log confirmed both:

```text
Formats: Original: cuda | HW: cuda | SW: p010le
pixfmt:cuda
```

No `hwdownload`, `hwupload_cuda`, `-f rawvideo`, CPU RGB buffer, or Python frame pipe occurred in any successful variant. The output was passed to NVENC as a CUDA hardware frame. `p010le` is selected as the CUDA frame's software format inside the CUDA filter graph; using output `-pix_fmt p010le` instead of `-pix_fmt cuda` caused software format negotiation and is not the native device-frame path.

### CUDA filters

The build exposes:

```text

```

`scale_cuda` accepts an output `format`, including `p010le`. `hwupload_cuda` explicitly uploads a system-memory frame, so it must not appear in a native NVDEC path. `hwdownload` explicitly downloads a hardware frame, so it is also forbidden for this probe.

`colorspace_cuda` in this build exposes only the `range` option. A direct `colorspace_cuda` operation on the decoder's `p010le` CUDA frame failed with:

```text
Unsupported pixel format: p010le
```

The working CUDA-only workaround is described in Variant 3 below.

```text

-c:v hevc_cuvid
```

```text

```

This is a CUDA `AVFrame` path, not software HEVC decode followed by a later upload.

## 3. NVDEC → NVENC test

### Variant 1: direct decoder frame to encoder

```text
hevc_cuvid -> hevc_nvenc
```

Command shape:

```text
ffmpeg -hwaccel cuda -hwaccel_device 0 -hwaccel_output_format cuda \
  -c:v hevc_cuvid -i BR2049_HDR.mkv -map 0:v:0 -frames:v 10 \
  -c:v hevc_nvenc -pix_fmt cuda \
  -color_range tv -color_primaries bt2020 \
  -color_trc smpte2084 -colorspace bt2020nc output.mkv
```

Result:

- process return code: `0`;
- frames encoded: `10`;
- output: `3840x1600`;
- zero-copy classification: **ZERO-COPY PASS**;
- no CUDA-to-CPU boundary observed.

This is the minimal proof that the current build can carry a CUDA frame from NVDEC directly to NVENC.

## 4. CUDA filter tests

### Variant 2: `scale_cuda`

```text
hevc_cuvid
  -> scale_cuda=w=1920:h=800:format=p010le
  -> hevc_nvenc
```

This performs an actual CUDA resize and emits a CUDA frame with `p010le` software format. The output was `1920x800` and encoded successfully as HEVC Main 10.

Result:

- process return code: `0`;
- frames encoded: `10`;
- zero-copy classification: **ZERO-COPY PASS**;
- `hwdownload`: absent;
- `hwupload_cuda`: absent;
- CPU rawvideo boundary: absent.

### Variant 3: CUDA colorspace/range and p010 path

The requested direct form was tested first but is not supported by this build:

```text
p010 CUDA -> colorspace_cuda
```

The filter rejected `p010le`. The working all-device path was:

```text
hevc_cuvid
  -> scale_cuda=format=nv12
  -> colorspace_cuda=range=tv
  -> scale_cuda=format=p010le
  -> hevc_nvenc
```

All three filters consume and emit CUDA frames. The temporary `nv12` surface is on the GPU; it is not a CPU buffer and does not introduce a host round-trip. The final frame is a `p010le` CUDA frame passed to NVENC with `-pix_fmt cuda`.

Result:

- process return code: `0`;
- frames encoded: `10`;
- output: `3840x1600`;
- zero-copy classification: **ZERO-COPY PASS**;
- required HDR10 metadata: passed.

The `nv12` intermediate is a feasibility workaround, not a recommendation for the eventual HDR transform path. It should be replaced by a device-side conversion that supports the required precision and color contract directly when the native transform is designed.

## 6. Timing

Each variant processed exactly 10 frames. The values below are from the second, final bounded run recorded in `P2.23_native_cuda_probe_results.json`.

### End-to-end process wall time

| Variant | Total wall | Bounded process throughput |
|---|---:|---:|
| 1: NVDEC → NVENC | **416.745 ms** | **23.996 FPS** |
| 2: NVDEC → `scale_cuda` → NVENC | **327.541 ms** | **30.531 FPS** |
| 3: NVDEC → CUDA colorspace/p010 → NVENC | **478.481 ms** | **20.899 FPS** |

These are 10-frame process-wall measurements including FFmpeg startup, demuxing, hardware initialization, codec scheduling, muxing, and encoder flush. They are not sustained long-run streaming FPS values. The lower wall time of Variant 2 is not an isolated `scale_cuda` speed claim because it also has different output dimensions and encoder workload.

### FFmpeg `-benchmark_all` counters

FFmpeg exposes codec task counters but does not expose a separate CUDA-filter task counter in this build. The reported `decode_video` values are FFmpeg decoder-task timing, not a complete GPU-engine occupancy measurement. `encode_video` and `flush_video` are kept separate because NVENC work is often completed during flush.

| Variant | decode/NVDEC task | encode task | encoder flush | encode + flush |
|---|---:|---:|---:|---:|
| 1 | **0.041 ms** | **2.405 ms** | **92.191 ms** | **94.596 ms** |
| 2 | **0.044 ms** | **3.892 ms** | **20.114 ms** | **24.006 ms** |
| 3 | **0.124 ms** | **4.925 ms** | **87.361 ms** | **92.286 ms** |

### CUDA processing timing limitation

`-benchmark_all` does not report `scale_cuda` or `colorspace_cuda` as an independent stage. Consequently:

- `cuda_processing_ms` is intentionally recorded as **not independently observable**;
- Variant 2 and Variant 3 total-wall deltas versus Variant 1 are only comparative process observations;
- they must not be presented as kernel timings;
- a native FFmpeg trace, CUDA events inside a custom filter, Nsight Systems, or an equivalent native instrumentation layer is required for independent CUDA-filter timing.

The probe therefore satisfies the architectural feasibility objective without inventing a CUDA kernel duration.

## 9. Limitations

- The experiment processed only the first 10 frames and did not render 5 seconds, 10 seconds, or the full film.
- The probe used the HDR HEVC BR2049 source, not the Open Matte composition and not the production renderer.
- No CuPy, P2.20 backend, CPU transform, luminance fitting, custom CUDA kernel, RGB conversion, or production composition was executed.
- `-benchmark_all` does not expose an independent CUDA-filter timer. Its decode counters are codec-task counters, not a full NVDEC hardware timing.
- Process-wall throughput includes FFmpeg startup, input probing/demux, CUDA context initialization, muxing, and encoder flush; it is not a steady-state pipeline benchmark.
- Variant 3 requires an `nv12` CUDA intermediate because this build's `colorspace_cuda` rejects `p010le` directly. The intermediate remains on-device but may not be acceptable for the final HDR precision contract.
- `nvidia-smi` memory readings are coarse snapshots and cannot prove exact allocation ownership.
- Metadata was explicitly set for the output; no image-quality or mathematical correctness claim is made for a future custom transform.
- The repository still has earlier unrelated workspace changes in `cli.py`, `core/config.py`, and `compose.py`, plus the pre-existing untracked P2.20 `transform_backend.py`. P2.23 did not modify or revert them. `transform.py`, `luminance.py`, and `pipeline/render.py` remained clean relative to the current HEAD.

## 10. Recommended architecture for the custom transform

Do not integrate the P2.20 CuPy backend directly into this path. The next native prototype should be a separate C++/CUDA or FFmpeg-filter boundary:

1. Create or receive a CUDA device context and an `AVHWFramesContext` for the selected GPU.
2. Let NVDEC produce `AVFrame`s with `format=AV_PIX_FMT_CUDA`; retain the decoder frame pool and its CUDA `sw_format` contract.
3. Implement the custom transform as a native CUDA-aware FFmpeg filter or a C++/CUDA extension that consumes the CUDA `AVFrame` planes directly.
4. Keep ownership and synchronization explicit: the transform CUDA stream must complete before the downstream filter or NVENC consumes the frame. Use CUDA events or the FFmpeg hardware-frame synchronization contract rather than a host synchronization/download.
5. Perform the device-side color conversion and HDR output preparation into a CUDA frame with `sw_format=p010le` and the required BT.2020/PQ/TV metadata.
6. Pass the resulting `AVFrame` directly to `hevc_nvenc` with the hardware pixel format `AV_PIX_FMT_CUDA` / `-pix_fmt cuda`.
7. Only after that native frame contract works should the P2.20 transform mathematics be mapped into a custom CUDA kernel. The existing `scale_cuda`/`colorspace_cuda` filters may be reused where their format and precision support is sufficient, but they are not a substitute for the custom transform.

### Required interface/API boundary

The likely required native boundary is:

```text
AVBufferRef* hw_device_ctx       // CUDA device
AVBufferRef* hw_frames_ctx       // CUDA frame pool
AVFrame*     decoder_cuda_frame  // format AV_PIX_FMT_CUDA
CUDA stream/event synchronization
AVFrame*     transformed_cuda_frame
AVFrame*     p010_cuda_frame
hevc_nvenc receives AV_PIX_FMT_CUDA frame
```

A C++/CUDA extension or a native FFmpeg filter is expected for the custom kernel because the current Python repository has no `AVHWFramesContext` ownership API, CUDA `AVFrame` wrapper, or custom CUDA-frame-to-NVENC bridge. Python can orchestrate a subprocess probe, as this harness does, but it cannot by itself expose the required device-frame contract for the transform.
