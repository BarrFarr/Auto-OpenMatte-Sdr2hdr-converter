# P2.24 Native CUDA Filter Feasibility Report

**Date:** 2026-08-15  
**Scope:** feasibility-only prototype gate for a native custom CUDA kernel between NVDEC and NVENC.  
**Decision:** **FAIL / BLOCKED** for the custom native filter in the current environment.  
**Production integration:** not attempted.  
**Custom probe:** not created because the native build gate failed.

## Executive answer

The existing computer can run the previously demonstrated built-in FFmpeg CUDA path:

```text
HEVC BR2049
  -> NVDEC / hevc_cuvid
  -> AVFrame with format=cuda
  -> built-in CUDA filter operation
  -> CUDA frame
  -> NVENC / hevc_nvenc
```

P2.23 proved that runtime path for exactly 10 frames and classified all three bounded variants as `ZERO-COPY PASS`.

P2.24 asked a narrower question: whether a **new native custom CUDA filter with a real CUDA kernel launch** can be built and inserted into that path. That question cannot be answered positively in this environment because the required native development components are absent:

- `nvcc`: **not found**;
- CUDA Toolkit root: **not found**;
- `CUDA_PATH`: **empty**;
- CUDA headers: **not found**;
- FFmpeg development headers: **not found**;
- `libavfilter` headers: **not found**;
- `libavutil` CUDA hardware-context headers: **not found**;
- FFmpeg development/import libraries: **not found**.

Only the NVIDIA driver-side runtime entry point was found at `C:\WINDOWS\System32\nvcuda.dll`. That DLL and the prebuilt `C:\ffmpeg\bin\ffmpeg.EXE` runtime are not sufficient to compile and link a native FFmpeg CUDA filter.

Therefore the answer for **custom native CUDA kernel in the current environment** is:

```text
BLOCKED — runtime capability exists, but native compilation/linking capability does not.
```

## 4. Custom filter architecture

### Required architecture

If the native SDK becomes available, the minimal feasibility filter should be a separate native prototype, not a production change:

```text
NVDEC
  -> AVFrame { format = AV_PIX_FMT_CUDA }
  -> P2.24_cuda_filter_probe
       - acquire/validate CUDA frame context
       - obtain device pointers and pitches
       - launch a deterministic identity/copy kernel
       - synchronize through CUDA event/stream ownership
  -> AVFrame { format = AV_PIX_FMT_CUDA }
  -> NVENC
```

The filter must use FFmpeg's hardware-frame contract, retain the CUDA device/frame context, and return a CUDA `AVFrame`. It must not use a CPU frame, `hwdownload`, `hwupload_cuda`, or a Python pixel buffer.

### What was not implemented

`P2.24_cuda_filter_probe` was intentionally **not created**. No C++/CUDA source, FFmpeg filter registration, DLL, static library, CMake project, or loadable filter artifact was produced because compilation was blocked before implementation.

No real CUDA kernel launch occurred in P2.24. The existing P2.23 `scale_cuda` and `colorspace_cuda` runs are built-in FFmpeg filter evidence only and must not be presented as proof of a user-authored kernel.

## 5. CUDA frame format and layout

### Evidence available from P2.23

P2.23 established the runtime frame contract at the FFmpeg graph level:

```text
format = cuda / AV_PIX_FMT_CUDA
software format = p010le
width = 3840
height = 1600
```

The source was HDR HEVC Main 10 with `yuv420p10le`, and the successful NVDEC/NVENC path retained CUDA hardware frames. The P2.23 log included the equivalent of:

```text
Formats: Original: cuda | HW: cuda | SW: p010le
pixfmt:cuda
```

P2.23 also demonstrated that this build's direct `colorspace_cuda` operation rejects `p010le`, while the CUDA-only workaround uses an `nv12` intermediate and returns to `p010le` before NVENC.

### Evidence not available in P2.24

Because no native filter was built, P2.24 did **not** inspect or log the native `AVFrame` fields required by the custom kernel:

- actual `AVFrame::data[]` device pointers;
- `AVFrame::linesize[]` values/pitches;
- exact plane count at the native filter boundary;
- `AVHWFramesContext` allocation parameters;
- CUDA surface/object handles;
- CUDA stream association;
- per-plane device memory allocation;
- copy/kernel completion events.

The filter must not assume contiguous memory or infer pitch from width. A future implementation must use each frame's supplied plane pointer and `linesize`/pitch, and must explicitly handle the negotiated `sw_format` (initially expected to be `p010le`, subject to the actual filter negotiation).

## 6. Kernel implementation

No kernel implementation exists in this workspace for P2.24.

The intended first kernel, once the SDK is available, is an identity copy over the negotiated CUDA surface(s):

```text
output plane sample = input plane sample
```

It would need to:

- receive device pointers;
- use width and height bounds;
- use the supplied pitch/stride rather than assuming tight packing;
- handle all negotiated planes and bit depth correctly;
- launch through the CUDA runtime/driver API;
- provide an explicit completion/synchronization contract to downstream FFmpeg/NVENC;
- preserve the input format and metadata.

No production transform math, BT.1886, BT.709 → BT.2020, luminance fitting, LUT, ratio, RGB scaling, PQ, or ROI processing was implemented or changed.

## 12. Future architecture for the full transform

This section is architectural only; no implementation was started.

Once a native filter can be built and the identity kernel is validated, the production mathematics would require a separate design pass covering:

- device-side input/output format negotiation for `p010le`/NV12 and any required RGB intermediate;
- BT.1886 and BT.709 → BT.2020 constants;
- luminance computation and precision requirements;
- log-curve and PQ square-root LUT storage and interpolation;
- ratio and RGB scaling operations;
- read-only constant memory versus per-frame/global buffers;
- whether conversion, luminance, LUT lookup, ratio, and output packing can be fused into one kernel;
- explicit handling of chroma subsampling and P010 plane layout;
- ROI bounds and pitch-aware addressing;
- CUDA stream/event synchronization with FFmpeg and NVENC;
- preservation of TV range and BT.2020/PQ metadata.

No conclusion about numerical equivalence, performance, or suitability for the existing transform is made by P2.24. In particular, this report does not authorize changes to the CPU backend, P2.20 CuPy backend, production renderer, or transform mathematics.

**P2.24 decision: FAIL / BLOCKED.**

A future attempt requires, at minimum, a native development environment containing:

1. CUDA Toolkit with `nvcc`, CUDA headers, runtime/driver development interfaces, and compatible host compiler;
2. FFmpeg development headers for `libavfilter`, `libavutil`, `libavcodec`, including CUDA hardware-context declarations;
3. FFmpeg link/import libraries or a reproducible FFmpeg source build with matching ABI/configuration;
4. a native C++/CUDA build/link target capable of producing a filter or extension loadable by the selected FFmpeg build;
5. a way to instrument CUDA events and inspect the negotiated `AVFrame` pointers, planes, and pitches.

Until those components are deliberately made available and compatibility is checked, the custom-kernel question remains blocked. Work stops here as required.
