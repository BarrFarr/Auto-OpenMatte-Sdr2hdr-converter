# P2.25 CUDA / FFmpeg Native Toolchain Feasibility Audit

**Date:** 2026-08-15  
**Scope:** read-only feasibility audit; no installation, system modification, `.venv` modification, compilation, custom filter, video render, commit, or push.  
**Decision:** **GO WITH CAUTION** for a future isolated toolchain; **NO-GO for system-wide installation in this task**.  
**Current custom-filter status:** still blocked by missing native development components.

## Executive answer

The current computer is suitable for CUDA runtime execution but not for building a native custom CUDA FFmpeg filter.

The existing runtime path remains available:

```text
NVDEC -> CUDA AVFrame -> built-in FFmpeg CUDA filter -> NVENC
```

P2.23 proved that path for 10 frames. P2.24 established that a user-authored native CUDA filter cannot be built here because the compiler, CUDA Toolkit development files, and FFmpeg development files are absent.

The driver and GPU are technically compatible with a future CUDA Toolkit installation. The safe route is not to replace the current runtime. It is to create a separate, explicitly selected build environment containing matching CUDA, host compiler, FFmpeg source/development files, and a dedicated native target.

The current prebuilt `C:\ffmpeg\bin\ffmpeg.exe` cannot load an arbitrary custom filter DLL as a drop-in plugin. A future implementation must choose one of these boundaries:

1. build a dedicated native host/application that owns FFmpeg `AVFrame`/CUDA hardware-frame calls and invokes a CUDA DLL; or
2. rebuild/relink a matching FFmpeg/libavfilter target with the custom filter registered, then use that dedicated FFmpeg executable.

No installation is recommended or performed by P2.25.

## 13. External filter DLL versus FFmpeg rebuild

### Option A: external DLL loaded by the current `ffmpeg.exe`

**Result: not available as a drop-in path.**

The stock FFmpeg CLI does not provide a generic mechanism where an arbitrary external CUDA filter DLL can be placed beside `ffmpeg.exe` and then named in a normal filter graph. The current executable is statically linked and has no matching `libavfilter` development interface exposed in `C:\ffmpeg`.

A standalone CUDA DLL could still be useful, but only if a separate native host explicitly:

- owns or receives the FFmpeg `AVFrame`;
- owns the CUDA `AVHWDeviceContext`/`AVHWFramesContext` contract;
- passes device pointers and pitches to the DLL;
- launches the kernel;
- synchronizes the CUDA stream/event;
- returns a valid CUDA `AVFrame` to downstream processing.

That is a new native application/bridge, not a plugin loaded by the existing executable.

### Option B: rebuild or relink a matching FFmpeg target

**Result: required for a custom filter in a normal FFmpeg filter graph.**

The direct route is to:

1. obtain the exact FFmpeg source version/configuration to target;
2. add/register the custom filter in a dedicated source/build tree;
3. compile it with matching FFmpeg headers, libraries, CUDA Toolkit, and host compiler;
4. produce a dedicated FFmpeg executable or matching shared `libavfilter`/`libavutil` stack;
5. run the CUDA filter graph against that dedicated build.

A complete rebuild of every FFmpeg dependency is not necessarily required if a matching shared/development package is used. However, the custom `libavfilter` and its host executable must be built and linked as one coherent ABI set. The current static `C:\ffmpeg\bin\ffmpeg.exe` cannot simply discover the new filter DLL.

### Preferred future architecture

For the stated goal of placing a custom kernel between NVDEC and NVENC, the preferred choices are:

- a dedicated FFmpeg source build containing a native CUDA-aware filter; or
- a dedicated C++/CUDA host using matching FFmpeg development libraries and a separate CUDA kernel library.

The second option avoids modifying the user's existing `C:\ffmpeg\bin` runtime but still requires a native host and FFmpeg development stack.

## 14. Python/native DLL alternative

The proposed direct path:

```text
Python
  -> native CUDA DLL
  -> CUDA pointer
  -> FFmpeg CUDA AVFrame
  -> NVENC
```

is not available through the current stock FFmpeg subprocess interface.

### Why direct Python `ctypes` is insufficient

The existing Python process can launch `ffmpeg.exe`, but the subprocess does not expose its internal CUDA `AVFrame`, `AVHWFramesContext`, device pointer, pitch, CUDA stream, or synchronization event to Python. A Python `ctypes` call therefore has no safe pointer handoff to the CUDA frame inside the separate FFmpeg process.

Passing an arbitrary integer pointer from Python would not solve:

- ownership and lifetime;
- device/context selection;
- `AVFrame` reference counting;
- CUDA stream ordering;
- plane/pitch validation;
- NVDEC/NVENC synchronization;
- error propagation.

### What would be possible

A Python front end could orchestrate a separately built native host process or extension. That native component would need to own the FFmpeg API calls and expose a narrow, validated C ABI to Python. Alternatives include:

- a dedicated C++/CUDA executable controlled by Python;
- a custom Python extension that embeds/uses matching FFmpeg libraries;
- a native host that calls a separate CUDA DLL while retaining all `AVFrame` and CUDA-context ownership.

Each alternative still requires the missing FFmpeg development stack and a coherent native ABI. No Python/native bridge was implemented in P2.25.

## 16. Risks

1. **Static FFmpeg versus external DLL mismatch:** the current executable has no plugin ABI or linkable `libavfilter` interface.
2. **FFmpeg ABI mismatch:** headers/libs from another build, even with similar version numbers, may not match the embedded ABI/configuration.
3. **Compiler/CRT mismatch:** current FFmpeg was built with MSYS2 GCC; a future MSVC DLL or host must not be assumed ABI-compatible with the existing executable.
4. **CUDA Toolkit/API drift:** CUDA 13.x is technically compatible with the driver/GPU, but current FFmpeg 7.1.1 plus a custom filter must be validated as a separate source build.
5. **CUDA header removals:** code using legacy texture/surface headers may need updating for CUDA 13.x.
6. **Environment contamination:** global PATH/CUDA_PATH or Visual Studio integration can affect other CUDA/CuPy projects.
7. **Driver/toolkit conflation:** `nvidia-smi` reporting CUDA 13.2 does not mean `nvcc` or development headers exist.
8. **Frame ownership and synchronization:** a native bridge must preserve `AVFrame` references, CUDA streams, pitches, and NVENC ordering; a raw pointer handoff is unsafe.
9. **Runtime output mismatch:** a new FFmpeg build must independently revalidate NVDEC, CUDA frame negotiation, NVENC, metadata, and zero-copy behavior.
10. **Installation size and rollback:** a full CUDA/Visual Studio setup is materially larger and less reversible than the current runtime-only setup; system restore/uninstall planning is required.

## 17. Recommendation

**Recommendation: GO WITH CAUTION.**

Why:

- The GPU and driver are technically suitable: RTX 3080 / SM 8.6, driver 595.79, driver-reported CUDA level 13.2.
- The existing runtime path already proves NVDEC/CUDA/NVENC feasibility.
- A native toolchain can be prepared in a separate build root without replacing the existing FFmpeg runtime.

- The project must choose a coherent native architecture and build a matching FFmpeg/native host stack.
- A system-wide installation is not considered safe enough to perform implicitly because it can affect PATH, CUDA selection, Visual Studio integration, and other CUDA/Python projects.

This is not a recommendation to install anything during P2.25. It is a recommendation that a future installation is technically worthwhile only if it is explicitly approved and isolated.
